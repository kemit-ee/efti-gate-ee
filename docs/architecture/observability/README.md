## Overarching rules

These are the cross-cutting invariants every sub-area in this theme derives from. AC bullets in the CFR files specialise them to specific endpoints, error codes, or DB state.

### 1.1 Logs are structured ECS records, not human-formatted strings

Every log line emitted by the gate is a JSON object conforming to **Elastic Common Schema (ECS) 8.x** with the `efti.*` extension namespace (see `docs/specs/logging-spec.md`). Log lines are written to stdout/stderr; the operator's log collector (Fluentbit, Vector, etc.) ships them to centralised storage. The gate never owns log files on disk and never tails them — that is a deployment concern.

### 1.2 Every request carries a correlation id

Every inbound request is tagged with a correlation id (`trace.id`) — either from an upstream header (`X-Request-ID`, `Trace-Parent`) or generated by the gate. The id propagates into the ECS log record, into outbound calls (gate-to-gate, gate-to-platform), and into the `X-Request-ID` header echoed back to the client. This lets operators trace a single business request across multiple gate nodes and across cross-gate hops.

### 1.3 Metrics are scrape-able Prometheus exposition

The gate exposes Prometheus exposition format on a dedicated `/metrics` endpoint (configurable port, default 9090). Metric names follow the `efti_*` namespace with the standard `_total` / `_seconds` / `_bytes` suffixes per the Prometheus naming conventions. There is no push-based metrics export. The gate does not own the metrics scrape interval; operators configure it. The gate does not own dashboards or alerting rules — those are deployment-time deliverables.

### 1.4 Alert thresholds are documented, not hard-coded

The gate publishes recommended alert thresholds (e.g. `db.pool < 2`, `heap > 80%`) in `docs/specs/logging-spec.md` §2.3 and `docs/specs/non-functional.md`, but it never enforces them at runtime. Alerting profiles are operator-owned and live in the deployment repo, not in the gate. This separation lets operators run multiple profiles (dev/staging/prod) without rebuilding the gate image.

### 1.5 PII redaction at log emit time

The log encoder strips sensitive fields before serialising: `Authorization`, `X-API-Key`, `X-Client-Cert-Subject`, JWT bodies, HTTP Basic credentials, full request bodies on Platform / Authority API endpoints (the dataset is the platform's, not ours to log). The redaction list is conservative — false positives are preferable to leaks.

### 1.6 No business event without an audit-log entry

The pair "log line + audit-log row" is the canonical record of a business-significant event (authorisation denial, dataset retrieval, admin mutation). Logs go to centralised observability storage (often Elasticsearch); audit-log rows go to the gate DB for compliance retention. The gate writes both atomically — if the audit row fails to INSERT, the request fails before any business effect.
